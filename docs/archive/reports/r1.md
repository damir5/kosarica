# Investigation: Why Ingestion Is Not Stopping When UI Shows All Done

## Executive Summary

The ingestion system appears complete in the UI, but background workers are stuck in an infinite retry loop due to **database lock contention** during concurrent price snapshot swaps. The root cause is a mismatch between:

1. **UI Status**: Based on `ingestion_runs` table (shows "completed")
2. **Actual State**: `task_queue` table has tasks stuck in retry loops (lock timeout failures)

## Root Cause: Database Lock Contention in `swapPriceSnapshot`

### Location
`/workspace/services/price-service/internal/handlers/task_cluster.go:1127-1325`

### The Problem

Multiple ingestion runs for the **same chain (konzum) and same target date** execute concurrently. Each uses:

```go
// Advisory lock to serialize access (line 1152)
lockKey := fmt.Sprintf("%s:%s", chainSlug, targetDate.Format("2006-01-02"))
tx.Exec(ctx, `SELECT pg_advisory_xact_lock(hashtext($1))`, lockKey)

// But lock_timeout is too short (line 1144)
tx.Exec(ctx, `SET LOCAL lock_timeout = '5s'`)

// DELETE from price_tiers takes 10+ seconds (line 1253-1258)
_, err = tx.Exec(ctx, `DELETE FROM price_tiers WHERE chain_slug = $1 AND target_date = $2`, ...)
```

### What Happens

1. **Transaction A** acquires advisory lock, begins slow DELETE from `price_tiers`
2. **Transaction B** waits for advisory lock, but `lock_timeout=5s` expires before A finishes
3. **Transaction B** fails with: `ERROR: canceling statement due to lock timeout (SQLSTATE 55P03)`
4. Task B is scheduled for retry in `(retry_count + 1) * 1 minute`
5. Repeat forever...

### Configuration

```
Import Semaphore: 4 slots (services/price-service/cmd/server/main.go:51)
lock_timeout: 5 seconds (too short for large DELETEs)
max_retries: 3 (default)
```

## Why UI Shows "All Done"

### Run Status vs Task Status Disconnect

The UI queries `ingestion_runs` table for stats:

```sql
-- services/price-service/internal/database/queries/runs.sql:37-46

    COUNT(*) as total_runs,
    COUNT(*) FILTER (WHERE status = 'completed') as completed,
    ...
FROM ingestion_runs
WHERE created_at >= $1 AND created_at <= $2
```

**But tasks are tracked separately in `task_queue` table - there's no join between them!**

### Runs Can Be "Completed" While Tasks Fail

In `task_finalize.go:44-57`, the finalize task marks the run as complete:


The finalize task is a **child of the cluster task**. It can complete successfully (just updates a row) while the parent cluster task is stuck retrying from lock failures!

### Retry Logic Analysis

From `0001_manual_functions.sql:65-91`:

```sql
CREATE OR REPLACE FUNCTION fail_task(p_task_id text, p_error_message text, p_retry boolean DEFAULT true)
RETURNS boolean
LANGUAGE plpgsql
AS $$
DECLARE
  should_retry BOOLEAN;
BEGIN
  SELECT retry_count < max_retries INTO should_retry FROM task_queue WHERE id = p_task_id;
  IF p_retry AND should_retry THEN
    UPDATE task_queue
    SET status = 'pending',
        retry_count = retry_count + 1,
        scheduled_for = NOW() + ((retry_count + 1) * INTERVAL '1 minute'),
        error_message = p_error_message,
        updated_at = NOW()
    WHERE id = p_task_id;
    RETURN TRUE;
  ELSE
    UPDATE task_queue
    SET status = 'failed',
        failed_at = NOW(),
        error_message = p_error_message,
        updated_at = NOW()
    WHERE id = p_task_id;
    RETURN FALSE;
  END IF;
END;
$$;
```

The logic **should** stop after 3 retries, but we're seeing 4+ failures. Possible causes:
- `retry_count` isn't incrementing properly
- A new task is being created instead of retrying
- The check `retry_count < max_retries` is somehow always true

## Recommended Fixes

### 1. Increase `lock_timeout` (Immediate)

**File:** `services/price-service/internal/handlers/task_cluster.go:1144`

```go
// Change from:
if _, err := tx.Exec(ctx, `SET LOCAL lock_timeout = '5s'`); err != nil {

// To:
if _, err := tx.Exec(ctx, `SET LOCAL lock_timeout = '30s'`); err != nil {
```

### 2. Fix Retry Logic Bug (High Priority)

Investigate why tasks are retrying beyond `max_retries=3`. The `fail_task` function should stop retrying after 3 attempts.

### 3. Better Run/Task Synchronization (Medium Priority)

The UI stats should reflect actual task status, not just run status. Consider:
- Adding a `pending_tasks` or `processing_tasks` count to the stats
- Only mark runs as "completed" when ALL child tasks are complete
- Adding a health check endpoint that shows stuck tasks

### 4. Chain-Level Locking (Architectural)

Current advisory lock: `chainSlug:targetDate` (e.g., "konzum:2026-01-31")

Problem: Multiple runs for the same chain on the same day will still contend.

Consider: **Chain-level locking** - only allow one ingestion run per chain at a time, regardless of target date.
