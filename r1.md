## Plan Review: Ingestion Task/Subtask Architecture

### Summary
Solid architecture addressing connection starvation and enabling proper deduplication. The item-level price tier approach is correct—store-level hashing was fundamentally broken for catalogs with any variation.

### Critical Issues

**1. SQL Injection Bug (URGENT)**
You mention a SQL injection in `CompleteTask()` at line 112. This needs immediate fixing regardless of this migration.

**2. Parent-Child Trigger Race Condition**
The completion trigger updates `completed_children` then checks if parent should proceed. Two subtasks completing simultaneously could both see `completed_children < expected_children` and neither trigger the parent. Use atomic compare-and-swap or single UPDATE with RETURNING.

### Architecture Concerns

**3. Cluster Phase Memory Pressure**
Loading all 188 stores × 20k items into memory for clustering could be 3.7M+ rows. Consider:
- Streaming JSON files one at a time
- Building item-price map with eviction (process items in batches)
- Or use external sort/merge if memory becomes issue

**4. Storage Backend Not Specified**
"Storage backend" is vague. Options:
- **Local disk**: Simple but not shared across workers
- **S3/GCS**: Scalable, requires credentials
- **PostgreSQL JSONB**: You're trying to avoid DB load
- **Redis**: Good middle ground

Recommend: Start with S3-compatible (MinIO for dev, S3 for prod). Add to Phase 2.

**5. Transaction Boundaries in Cluster**
"Single transaction per price group" could still be heavy. Consider:
- Batch inserts of 1000 refs at a time
- Savepoint per batch for partial retry
- Or use COPY for bulk insert

### Schema Feedback

**6. Missing Indexes**
Add these for query performance:
```sql
CREATE INDEX idx_price_tiers_chain_item ON price_tiers(chain_slug, retailer_item_id);
CREATE INDEX idx_store_price_refs_store ON store_price_refs(store_id);
```

**7. Task Queue Parent Query Performance**
The `WHERE parent_task_id IS NOT NULL` index is good, but queries will also filter by status. Consider:
```sql
CREATE INDEX idx_task_queue_parent_status ON task_queue(parent_task_id, status) 
WHERE parent_task_id IS NOT NULL;
```

### Implementation Order Suggestion

**Phase 1.5: Fix SQL Injection** (Do this first)
**Phase 2: Add Storage Interface** (Define before handlers)
**Phase 3: Schema Changes** (Run migrations)
**Phase 4: Task Infrastructure** (Parent-child support)
**Phase 5: Handlers** (Discover → Fetch → Cluster → Finalize)
**Phase 6: Worker Pools** (Dedicated pools)
**Phase 7: Optimizer Updates** (Cache reads from new schema)
**Phase 8: Migration & Cleanup**

### Questions

1. **Storage backend choice?** (S3 vs disk vs other)
2. **What's the SQL injection bug details?** (Need to fix immediately)
3. **Rollback strategy?** If cluster phase fails mid-run, how do you resume without re-fetching all files?

### Verdict

**Approve with modifications.** Fix the SQL injection first, clarify storage backend, add suggested indexes, and watch for the parent trigger race condition. The item-level tier approach is the right fix for the deduplication problem.
